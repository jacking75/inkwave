## 1. 적용 원칙과 코드 경계

공통 게임 클라이언트는 사용자가 선택한 TypeScript + three.js로 확정하며 기존 코드와 자산을 재사용한다. 필요한 플랫폼 구현은 C#을 우선한다. 직접 작성하는 게임·클라이언트·플랫폼 구현 코드는 TypeScript 또는 C#으로 한다. Java·JavaScript·Kotlin·Swift로 새 구현을 추가하지 않고 Rust·Cargo·Rust 기반 모바일 셸도 도입하지 않는다. TypeScript를 브라우저용 JavaScript로 변환한 출력과 SDK·빌드 도구가 생성하는 코드는 직접 작성한 구현 코드와 구분한다. HTML·CSS·JSON은 UI·리소스·설정에 사용한다.

Android 빌드에는 Android SDK를 사용하며 필요한 Java·JDK·빌드 도구를 허용한다. 사용자가 말한 `ADK`는 Android SDK를 뜻한다고 확인했다. 공통 클라이언트는 TypeScript로 구현하며 모바일 셸과 필요한 C# 플랫폼 구현의 구체적인 범위는 스테이지 1 완성 후 M01에서 검토한다. 아래 Capacitor 절차는 후보 예시로만 남기고, 선택 전에는 설치·설정·플랫폼 코드 작성을 진행하지 않는다.

웹·안드로이드·아이폰을 지원 대상으로 하며 개발 중 기본 검증은 웹에서 수행한다. 스테이지 1 완성은 사용자와 확정한 캠페인 1장 전체인 1-1·1-2·1-3의 완성을 뜻한다. 세 임무의 웹 검증을 완료한 뒤 모바일 앱을 검토하고, 안드로이드 빌드는 사용자의 별도 요청 후에만 진행한다. 패드가 없는 PC·모바일에는 가상 키를 제공한다.

이번 산출물은 구현할 방법을 적은 문서이다. 아래 새 파일명·인터페이스·코드 조각은 제안이며 저장소에 해당 구현이 이미 존재한다는 뜻이 아니다. 정적 확인 기준은 커밋 `6687c624db31ddf87ccdac58c19045643aa8eddf`이다.

### 1.1. TypeScript 실행 경로의 준비 — W00

브라우저는 TypeScript 소스를 그대로 실행하지 않으므로 컴파일·개발 서버·산출물 경로를 먼저 정한다. 기존 `npm run serve`는 현재 JavaScript 게임을 실행하는 경로이며 `.ts`만 추가한다고 새 코드가 실행되는 것은 아니다.

W00에서는 TypeScript 설정과 개발·타입 검사·웹 산출물 생성을 연결한다. 기존 JavaScript를 재사용하는 이전 기간과 최종 TypeScript 구현을 구분하고, 변경 모듈부터 타입을 적용한다. JavaScript를 TypeScript라고 이름만 바꾸거나 전체 프로젝트에 타입 검사를 생략하는 정책을 최종 상태로 삼지 않는다. [TypeScript 공식 소개](https://www.typescriptlang.org/docs/handbook/typescript-in-5-minutes.html)를 언어·출력 관계의 근거로 삼는다.

기존 import map·저장소에 포함된 three.js·리소스 상대 경로·음원 생성 절차와 호환되는지 확인한다. 개발 서버는 변경 결과를 읽어야 하며, 모바일이 가져갈 `dist/`에는 `.ts` 소스가 아닌 실행 가능한 JavaScript와 리소스가 있어야 한다. 기존 파일 복사 빌드만으로 TypeScript 처리를 완료했다고 판정하지 않는다. 구체적인 컴파일러·번들러 구성은 W00 구현 시 호환성을 확인해 정하며 이 문서 작업에서 패키지를 설치하지 않는다.

## 2. 입력 상태와 성능 상태의 분리 — W01

### 2.1. 독립적으로 관리할 상태

| 상태 | 의미 | 변경 원인 |
|---|---|---|
| `hardwareProfile` | 실제 기기의 화면·GPU·메모리 제약을 판단한 성능 분류이다. | 초기 환경 확인과 사용자의 화질 선택이다. |
| `padStatus` | `unavailable`, `awaitingGesture`, `unmapped`, `ready`와 선택한 패드를 담는다. | API·권한·사용자 조작·연결 상태·매핑 확인이다. |
| `activeInputSource` | 최근 의미 있는 조작을 한 `gamepad`, `virtual`, `keyboardMouse`이다. | 데드존을 넘는 축이나 실제 버튼·포인터 조작이다. |
| `virtualControlsVisible` | 가상 키가 화면에 표시되는가이다. | 패드 사용 가능 여부와 자동/항상 표시 설정이다. |
| `virtualControlsEnabled` | 현재 전투 가상 키가 입력을 받아도 되는가이다. | 전투·메뉴·일시 정지·화면 방향·포커스 상태이다. |
| `inputContext` | `gameplay`, `menu`, `map`, `textEntry` 중 현재 소비 대상이다. | 게임 상태와 화면 전환이다. |

PC에서 가상 키를 표시한다고 `hardwareProfile`을 모바일로 바꾸지 않는다. 모바일에 패드를 연결해 가상 키를 접어도 모바일의 성능 프로필과 안전 영역·방향 정책을 유지한다. 에임 보조와 시점 감도도 가상 키의 표시 여부가 아닌 실제 입력 출처에 따라 선택한다.

기존 `touchMode`가 `memK`, 그림자 기본값, 렌더러 구성과 환경 생성에 사용되는 경로를 모두 확인해 목적에 맞는 새 상태로 바꾼다. 사용자에게 이미 저장된 `qualityChosen`, `shadowsChosen`은 존중한다. 입력을 바꾼다고 월드를 다시 만들거나 사용자 화질 설정을 덮어쓰지 않는다.

### 2.2. 설정 이전

새 설정은 예를 들어 `virtualControls: 'auto' | 'always'`, 가상 키 배치·크기·불투명도, 패드·가상 시점 감도를 가진다. 기존 `touchControls: 'on'`은 `always`로, `auto`와 `off`는 새 기본 `auto`로 이전하되 패드가 없으면 기본 조작을 사용할 수 있게 한다. 기존 잠수·발사 조작의 의미와 캠페인 저장은 변경하지 않는다.

설정 이전은 버전 값을 사용해 한 번만 수행한다. 이전 값을 읽을 수 없으면 안전한 기본값으로 복구하고 매 실행마다 사용자가 고른 값을 덮어쓰지 않는다.

## 3. 공통 입력 프레임과 소비 순서 — W02·W04

### 3.1. 제안하는 데이터 계약

```ts
// 설계 예시이다. 실제 구현을 완료한 코드가 아니다.
const inputFrame = {
  context: 'gameplay',
  source: 'virtual',
  move: { x: 0, y: 0 },
  lookDelta: { yaw: 0, pitch: 0 }, // 이 프레임의 각도 변화, rad이다.
  lookRate: { yaw: 0, pitch: 0 },  // 스틱의 각속도, rad/s이다.
  cursorDelta: { x: 0, y: 0 },    // 메뉴·지도 커서용 CSS px이다.
  navigation: { x: 0, y: 0 },     // 메뉴의 방향 입력이며 이동과 별도로 소비한다.
  actions: {
    fire: { held: false, pressed: false, released: false },
    squid: { held: false, pressed: false, released: false },
    jump: { held: false, pressed: false, released: false },
    sub: { held: false, pressed: false, released: false },
    special: { held: false, pressed: false, released: false },
    map: { held: false, pressed: false, released: false },
    pause: { held: false, pressed: false, released: false },
    confirm: { held: false, pressed: false, released: false },
    cancel: { held: false, pressed: false, released: false },
    tabPrev: { held: false, pressed: false, released: false },
    tabNext: { held: false, pressed: false, released: false },
  },
};
```

`move.x`는 오른쪽이 양수이며 `move.y`는 전진이 양수이다. 따라서 표준 패드의 세로 축은 부호를 반전해 변환한다. `move`는 길이 1 이하로 제한한다. 키보드·가상 키·패드의 이동을 무조건 더해 더 빨라지게 하지 않는다. 의미 있는 마지막 이동 장치를 선택하고 중립 전환과 데드존을 적용한다. 행동 버튼은 같은 액션으로 모은 뒤 한 번만 실행한다.

짧은 탭은 down/up이 같은 프레임 사이에 발생해도 `pressed`를 한 번 전달한다. 연속 발사·충전·잠수는 `held`와 `released`를 구분한다. `pressed`를 모든 무기에 자동 한 발을 쏘라는 뜻으로 쓰지 않고 기존 무기 실행기의 입력 의미에 맞게 연결한다.

마우스·터치의 이동량과 패드의 축을 같은 단위로 더하지 않는다. 포인터 이동은 감도로 각도 변화에 변환하고, 스틱은 각속도로 변환한 뒤 `dt`를 한 번 곱한다. 지도 컨텍스트는 `cursorDelta`를 소비하고 같은 입력으로 카메라까지 돌리지 않는다.

### 3.2. 프레임의 처리 순서

1. 이벤트로 누적한 키·포인터 상태와 게임패드 값을 읽는다.
2. 연결·해제·매핑 변경을 처리하고 필요하면 이전 상태를 초기화한다.
3. 현재 컨텍스트와 장치별 소유권을 기준으로 공통 프레임을 만든다.
4. 전투는 플레이어 제어기, 메뉴는 `nav()`, 지도는 지도 커서가 입력을 소비한다.
5. 실제로 소비한 입력 출처에 맞춰 버튼 안내와 가상 키 표시를 갱신한다.
6. 모든 소비가 끝난 뒤 `pressed`, `released`, 포인터 누적 이동량을 정리한다.

패드 메뉴 반복은 현재 `_padMenus()`의 고정 `1 / 60` 감소 대신 실제 `dt`를 사용한다. 낮은 프레임에서도 메뉴가 과도하게 빠르거나 느리게 움직이지 않도록 최초 반복 지연과 이후 반복 간격을 구분한다.

`Input`의 기존 `down()`, `wasPressed()`, `padButton()` 등은 마이그레이션 중 호환 경로로 유지한다. 플레이어·메뉴·지도 순서로 소비자를 옮기며, 같은 컨텍스트에서 기존 원시 입력 경로와 새 액션 경로가 동시에 실행되지 않게 한다.

## 4. Xbox 360 기준 게임패드

사용자와 확정한 Xbox 360 기준은 버튼 배치와 조작 방식이다. OS와 브라우저 또는 앱에서 인식되는 호환 게임패드를 지원한다. 실물 Xbox 360 패드의 연결을 모든 기기의 필수 조건으로 두지 않는다. 아래 매핑과 각 기기의 실제 패드 연결·입력 검증은 구분한다.

### 4.1. 표준 매핑과 게임 조작

다음 인덱스는 브라우저가 표준 매핑을 제공할 때 사용한다. 위치·인덱스는 [W3C 매핑 정의](https://www.w3.org/TR/gamepad/#remapping), 행동 연결은 기존 플레이어·메뉴 코드와 이번 프로젝트의 결정이다.

| Xbox 표기 | 표준 입력 | 전투에서의 의미 | 메뉴에서의 의미 |
|---|---|---|---|
| 왼쪽 스틱 | axes 0·1이다. | 카메라 기준 이동이다. | 선택 항목 이동이다. |
| 오른쪽 스틱 | axes 2·3이다. | 시점·조준이다. | 필요한 지도·목록 커서에만 연결한다. |
| A | button 0이다. | 점프·기존 회피 동작이다. | 확인이다. |
| B | button 1이다. | 별도 신규 공격을 할당하지 않는다. | 취소·뒤로 가기이다. |
| X | button 2이다. | 기존 모드에서 필요한 경우만 사용한다. | 기존 보조 메뉴 동작이다. |
| Y | button 3이다. | 스페셜이다. | 화면이 안내하는 보조 동작이다. |
| LB·RB | buttons 4·5이다. | RB는 보조 무기이며 LB는 신규 필수 행동을 넣지 않는다. | 이전·다음 탭이다. |
| LT·RT | buttons 6·7의 아날로그 값이다. | LT는 잠수, RT는 발사이다. | 메뉴를 관통해 발사하지 않는다. |
| Back | button 8이다. | 지도 표시이다. | 화면별 보조 안내를 따른다. |
| Start | button 9이다. | 로컬 일시 정지이다. | 일시 정지 화면에서 재개이다. |
| LS·RS 누름 | buttons 10·11이다. | RS의 기존 스페셜 별칭은 유지 가능하다. | 필수 메뉴 조작으로 강제하지 않는다. |
| 방향키 | buttons 12~15이다. | 지도에서는 기존 목적지 선택이며, 캠페인에 없는 아군 점프를 새로 만들지 않는다. | 상하좌우 이동이다. |
| Guide | button 16이다. | OS에 예약될 수 있어 필수 입력으로 쓰지 않는다. | 필수 입력으로 쓰지 않는다. |

기존 연습 모드에는 Back을 장비 화면에 쓰는 경로가 있다. 전투·연습·지도 컨텍스트를 명시해 같은 누름으로 두 화면을 열지 않게 하고, 충돌하는 장비 진입은 일시 정지 메뉴에서도 제공한다. 캠페인의 복구 단말은 기존 기획의 접근·범위 유지 방식이며 새 상호작용 키를 필수로 추가하지 않는다.

### 4.2. 연결과 재연결

- `navigator.getGamepads()`가 없거나 오류·접근 제한이 있으면 패드를 사용할 수 없는 상태로 처리하고 가상 키를 제공한다.
- 처음에는 패드가 노출되지 않을 수 있으므로 시작 화면에서 패드 버튼 입력을 안내한다. 이벤트만 기다리지 않고 프레임 폴링도 사용한다.
- 선택한 패드는 `index`를 포함한 세션 상태로 유지한다. 매 프레임 첫 번째 패드로 갈아타거나 두 패드 입력을 합치지 않는다.
- 연결 해제·장치 교체·매핑 변경 시 `padPrev`, `padPressed`, 스틱 보간·부스트, 트리거 상태를 초기화한다.
- 새 패드나 복귀한 패드의 상태는 중립 확인 후 활성화한다. 이미 누른 RT·A가 자동 발사나 메뉴 확인으로 들어가지 않게 한다.
- 축은 데드존을 적용한 뒤 의미 있는 조작으로 판정한다. 작은 드리프트로 입력 안내와 가상 키가 반복해서 바뀌지 않게 한다.
- 진동은 지원되는 경우에만 호출한다. 진동이 없다고 기본 조작을 막지 않는다.

비표준 `mapping` 패드는 검증된 프로필이나 사용자의 매핑 설정으로 표준 액션에 연결한다. 현재 코드처럼 임의 패드의 원시 인덱스를 그대로 Xbox 배치라고 가정하는 fallback은 제거한다. OS에서 인식되지만 매핑이 필요한 패드에는 현재 상태와 설정 진입을 알려 준다.

스틱의 초기 데드존은 기존 0.11~0.14 범위를 출발점으로 삼는다. 트리거는 예를 들어 누름 0.30·해제 0.20의 히스테리시스를 사용해 경계 떨림을 줄인다. 두 값은 실제 패드로 조정할 초기값이며 확정된 호환성 수치가 아니다.

## 5. 공통 가상 키 — W03

### 5.1. 공통 배치

| 영역 | 행동 | 전달 규칙 |
|---|---|---|
| 왼쪽 아래 이동 스틱 | 전후좌우 이동이다. | 원점 대비 방향·크기를 정규화해 `move`로 전달한다. |
| 오른쪽 화면 드래그 | 시점·조준이다. | 포인터 이동량을 시점 변화로 변환한다. |
| 발사 버튼 | 연속·충전·발사이다. | 누름·유지·해제를 보존하며 드래그 조준을 함께 허용한다. |
| 잠수 버튼 | 잠수·잉크 보충·벽 접근이다. | 기본은 누르고 있는 동안 유지한다. |
| 점프·보조·스페셜 버튼 | 각 행동이다. | 무기·행동의 유지/한 번 누름 규칙을 보존한다. |
| 지도·일시 정지 | 화면 전환이다. | 지도는 가상 키에서 토글을 허용하고 닫기 버튼을 제공한다. 정지는 한 번 실행한다. |

버튼은 중요한 HUD와 목표·위험 예고를 가리지 않게 배치한다. 가상 키가 없어도 모바일은 횡화면 기준으로 플레이하며 세로 화면에서는 전투를 멈추고 회전을 안내한다. 기기 방향은 `virtualControlsVisible`과 독립적으로 판단한다.

### 5.2. 모바일 멀티터치

`pointerId`별로 이동·시점/발사·행동 버튼의 역할을 유지한다. 이동 중 다른 손가락으로 조준·발사하거나 잠수·점프를 눌러도 첫 손가락의 역할을 뺏지 않는다. 손가락이 버튼 밖으로 이동하거나 `pointercancel`이 오면 소유한 역할과 눌림을 해제한다. 동일 동작의 여러 포인터는 소유권·참조 수를 관리해 한 손가락 해제가 다른 손가락의 누름을 지우지 않게 한다.

현재의 단일 이벤트 계층과 좌표 기반 hit test를 먼저 확장한다. 기존에는 메뉴 입력을 빼앗지 않으려고 강제 pointer capture를 사용하지 않으므로, 검증 없이 전면 도입하지 않는다. `lostpointercapture`가 발생하는 경로를 추가한다면 같은 취소 정책으로 연결한다.

### 5.3. PC의 마우스·펜

가상 키는 터치 장치 여부와 무관하게 생성할 수 있어야 한다. `_down/_move/_up`의 터치 전용 조건을 입력 출처와 UI 영역 기준으로 바꾼다. 마우스로 가상 키를 클릭할 때 pointer lock을 강제하지 않고, 클릭이 기존 마우스 발사 경로로 중복 전달되지 않게 한다.

마우스 하나로 이동 스틱을 계속 잡고 조준·발사를 동시에 할 수는 없으므로 PC용 가상 이동은 방향 클릭 유지와 중앙 정지 버튼을 제공하는 방식으로 설계한다. 선택한 방향을 눈에 보이게 표시하고, 중앙 정지·포커스 이탈·메뉴 진입·장치 전환으로 즉시 해제한다. 이후 오른쪽 영역에서 조준하고 발사할 수 있어야 한다. 터치의 손가락 유지 방식과 PC의 방향 유지 방식을 몰래 혼용하지 않고 설정과 안내에 표시한다.

기존 키보드 이동과 마우스 조준은 보조로 유지한다. PC에서 가상 키를 보여 주기만 하고 실제로는 키보드가 없으면 메뉴·전투를 진행할 수 없는 상태는 완료로 보지 않는다. PC 단일 포인터와 모바일 다중 포인터 검증은 별도로 수행한다.

### 5.4. 안전 영역과 반응형 처리

`viewport-fit=cover`가 이미 있으므로 배치 계산에서 `env(safe-area-inset-*)`를 반영한다. CSS에만 여백을 주고 JavaScript hit test 좌표는 기존 위치에 남기는 오류를 피한다. 같은 배치 결과를 렌더링과 hit test 양쪽에 사용한다.

주소창·소프트 키보드·회전·`visualViewport` 변경 시 포인터 상태를 취소하고 좌표를 다시 계산한다. 가장자리 시스템 제스처 영역을 피하며 버튼의 초기 최소 크기는 48 CSS px을 출발점으로 실제 기기에서 조정한다. 화면 전체의 확대나 입력을 무조건 막기보다 게임 조작 영역과 텍스트·메뉴 영역의 역할을 구분한다.

## 6. 장치 전환·생명주기·메뉴 — W04

| 사건 | 입력 처리 | 게임·화면 처리 |
|---|---|---|
| 패드 실제 조작 시작 | 가상 이동 유지·기존 포인터 역할을 지우고 패드 상태를 기준으로 시작한다. | 자동 모드의 가상 키를 접는다. |
| 가상 키 조작 시작 | 패드의 미세 드리프트를 무시하고 해당 가상 입력의 소유권을 부여한다. | 가상 프롬프트로 바꾼다. |
| 패드 연결 해제 | 모든 행동·축·이전 버튼 상태를 중립화한다. | 가상 키를 복원하고 로컬 캠페인은 일시 정지해 재개를 기다린다. |
| 메뉴·지도 열기 | 전투 유지 입력을 지운다. 같은 프레임의 확인/발사를 한 컨텍스트에서만 소비한다. | 메뉴 탐색 또는 지도 커서로 연결한다. |
| `blur`·숨김·앱 비활성화 | 키·가상 포인터·지도 토글·패드 에지·카메라 누적량을 지운다. | 로컬 게임을 정지하고 소리를 정리한다. |
| 다시 활성화 | 현재 장치와 중립 상태를 새로 읽는다. | 자동 발사·자동 재개 없이 사용자의 재개 동작을 기다린다. |
| 화면 회전 | 가상 키 역할과 PC 방향 유지를 취소한다. | 레이아웃과 안전 영역을 다시 계산한다. |

초기화는 `releaseAll(reason)` 같은 단일 경로에서 수행하고, 현재 `Input.releaseAll()`이 다루지 않는 지도 토글·패드 이전 상태·터치 에지·컨트롤러 보간 상태도 포함한다. 메뉴나 정지에서 복귀할 때 이전 클릭이 다시 소비되지 않도록 한다.

온라인 경기에서는 자신의 입력 중립화와 재연결 UI를 처리하며 다른 참가자의 시뮬레이션을 로컬 캠페인처럼 일괄 정지시키지 않는다. 백그라운드에서 서버 연결이 유지된다고 가정하지 않는다.

플랫폼 API는 처음부터 게임 객체 곳곳에 직접 넣지 않는다. TypeScript 경로의 `platform.ts`는 실행 환경, 앱 활성화 통지, 저장 접근·화면 기능을 좁은 인터페이스로 제공한다. C# 호스트를 선택하면 해당 경계의 플랫폼 구현을 C#으로 제공한다. 웹에서는 기존 API로 동작하고, 네이티브 셸이 없어도 부팅할 수 있어야 한다.

## 7. 웹 개발과 저장 — W05

현재 게임의 기본 실행은 저장소 루트의 `npm run serve`와 `http://localhost:8490`이다. TypeScript 전환 후의 개발 명령은 W00에서 새 컴파일 경로와 함께 확정한다. 현재 명령의 존재를 확인했으며 이번 문서 작업에서 서버를 실행한 것은 아니다. 로컬 웹 반복 개발을 위해 Android SDK나 Xcode를 설치하지 않는다.

패드 웹 검증은 HTTPS 또는 해당 브라우저가 신뢰할 수 있는 로컬 환경에서 수행한다. 휴대전화가 PC의 LAN IP에 일반 HTTP로 접속한 결과를 Gamepad API 지원의 최종 판정으로 사용하지 않는다. 실제 `isSecureContext`, API 노출·오류·사용자 버튼 조작 후 상태를 확인한다. 프레임 속도·화면 에뮬레이션으로 실제 Bluetooth·USB 입력을 대신하지 않는다.

저장 접근은 기존 프로필과 캠페인 데이터를 구분한다. 웹의 `localStorage` 데이터를 그대로 앱이 공유한다고 가정하지 않는다. 브라우저·도메인·앱 WebView의 저장 영역은 별도일 수 있으므로 이동이 필요하면 기획의 내보내기·가져오기를 명시적으로 제공한다. 자동 클라우드 동기화나 새로운 계정 시스템을 이번 전환의 필수 기능으로 추가하지 않는다.

임무 완료와 같은 의미 있는 시점에 저장하며 앱 종료 이벤트에서만 저장하지 않는다. 모바일 저장을 선택할 때도 완료 처리 ID·미확정 보상·중복 방지의 캠페인 규칙을 유지한다. 플랫폼별 저장 구현 교체가 보상 로직의 분기가 되지 않게 한다.

| 스테이지 1 완성 후 | 캠페인 1장 전체인 1-1·1-2·1-3의 웹 검증을 완료한 뒤 목표 기기·OS·패드·메모리·성능 문제를 검토한다. |
| 별도 Android 빌드 요청 후 | 언어 조건에 맞게 확정한 모바일 셸·SDK 요구사항을 고정하고 필요한 패키지와 Android 프로젝트를 만든다. |
| Android 통합 | 검증된 `dist/`를 Android 셸에 복사하고 입력·저장·생명주기·CSP·네트워크를 실기기로 확인한다. |
| 별도 iOS 작업 요청 후 | macOS·Xcode에서 iOS 셸을 만들고 WKWebView·패드·오디오·안전 영역·복귀 동작을 확인한다. |

아래는 후보인 Capacitor의 TypeScript 설정 예시이다. 직접 구현하는 플랫폼 확장까지 TypeScript·C# 조건을 충족하는지 검토한 뒤 모바일 셸을 정한다. 다른 셸을 선택하면 이 예시를 해당 방식으로 교체한다. 실제 설정 파일은 만들지 않으며 `appId`도 아직 정하지 않았다.

```ts
// 향후 capacitor.config.ts의 설계 예시이다.
// appId와 appName은 모바일 제작 시 확정한다.
export default {
  webDir: 'dist',
};
```

실제 모바일 단계의 순서는 웹 산출물 생성 → 대상 플랫폼 동기화 → 대상 IDE·기기 실행 → 결과 확인이다. Android만 작업할 때에는 `npx cap sync android`처럼 플랫폼을 명시해 요청하지 않은 iOS 작업까지 묶지 않는다. 이 문서의 명령은 미래 절차 설명이며 지금 실행할 지시가 아니다. [공식 개발 흐름](https://capacitorjs.com/docs/basics/workflow)을 근거로 한다.

`dist/`는 현재 빌드 스크립트가 다시 구성하는 출력 폴더이다. 네이티브 프로젝트나 서명 파일을 `dist/` 안에 만들지 않는다. 로컬 HTML·ES 모듈·import map·three.js 리소스·음원·글꼴의 상대 경로가 패키지 안에서 해석되는지 확인한다. 개발 서버 URL에만 연결되는 상태로 배포 앱을 만들지 않는다.

### 8.2. 모바일의 게임패드 연결

먼저 WebView에서 웹 Gamepad API를 그대로 검증한다. 표준 매핑·아날로그 트리거·해제 통지가 정확하면 그 경로를 사용한다. OS가 패드를 인식하지만 WebView가 필요한 입력을 전달하지 못하면 모바일 단계에서만 네이티브 입력 전달을 추가한다.

Android 네이티브 입력은 플랫폼의 버튼·축 값을 정규화해 같은 프레임 계약으로 보낸다. 트리거가 축과 버튼 이벤트를 모두 보낼 때 중복 발사를 막아야 한다. 이 주의점은 [Android 공식 컨트롤러 문서](https://developer.android.com/games/sdk/game-controller/controller-input)에 근거한다. iOS는 필요한 경우 Game Controller 프레임워크를 검토하며 실제 지원 패드와 OS를 기기에서 확인한다.

하나의 장치에서 웹 Gamepad API와 네이티브 전달을 동시에 소비하지 않는다. TypeScript로 구현한 웹 입력과 C# 플랫폼 입력 중 선택한 경로 하나만 활성화하고, 연결 해제와 백그라운드 전환을 공통 초기화에 연결한다. 작은 프레임 입력은 최신 상태를 우선하고 오래된 입력을 큐로 계속 재생하지 않는다.

네이티브 전달은 설계상의 보완 경로이며 지금 설치할 플러그인을 확정한 것이 아니다. 선택한 호스트에서 C#으로 플랫폼 입력을 전달할 수 있는지 검토한다. Capacitor의 네이티브 플러그인을 그대로 C#으로 작성할 수 있다고 가정하지 않는다. 플러그인 지원 상태와 유지보수를 실제 모바일 작업 시 확인한다. 직접 작성하는 추가 코드는 TypeScript·C# 범위로 제한하고 Java·Rust는 직접 작성하지 않는다. 제약을 발견하면 구현 전에 사용자에게 해당 선택 하나를 확인한다.

### 8.3. 그래픽·오디오·네트워크

모바일은 낮은 화질을 초기값으로 검토하고 잉크 아틀라스·그림자·후처리·해상도·동시 효과를 실제 프레임 시간과 메모리 상태로 조정한다. 가상 키를 껐다고 높은 화질로 바꾸지 않는다. 기존 웹 셰이더·WebGL 기능이 앱에서도 동작하는지 확인한다.

오디오는 사용자 시작 입력 후 활성화하고 앱 비활성화에서 중단·복귀를 처리한다. 전체 화면·방향 잠금 API의 성공을 필수 전제로 삼지 않고 미지원·실패 시 화면 내 안내로 처리한다.

온라인 연결이 필요한 모드는 실제 앱 Origin과 서버 허용 정책·CSP를 확인한다. 개발을 편하게 하려고 모든 Origin·모든 cleartext 연결을 일괄 허용하지 않는다. 단일 플레이 저장·콘텐츠를 서버 연결에 불필요하게 종속시키지 않는다.

## 9. 단계별 검증 사례와 판정

아래는 이후 구현에서 수행할 검사이다. 이번 문서 작성에서 통과했다고 주장하지 않는다.

| ID | 시나리오 | 잡으려는 오류 | 판정 기준 |
|---|---|---|---|
| T01 | PC에서 패드 없이 시작한다. | 터치 장치 판별 때문에 가상 키가 보이지 않거나 클릭이 무시되는 오류이다. | 마우스로 가상 키와 메뉴를 실제 사용할 수 있다. |
| T02 | PC 가상 이동을 유지하며 조준·발사한 뒤 정지한다. | 단일 마우스의 동시 조작 불가와 이동 유지 해제 누락이다. | 키보드 보조 없이 해당 행동을 수행하고 즉시 멈춘다. |
| T03 | 모바일에서 이동·발사/조준·점프를 겹친다. | 포인터 소유권 충돌과 누름이 사라지는 오류이다. | 서로 다른 손가락 역할이 유지되고 해제 후 남지 않는다. |
| T04 | 프레임 사이에 짧게 눌렀다 뗀다. | 짧은 탭 누락과 두 번 실행이다. | 액션 에지가 한 번 전달된다. |
| T05 | 같은 축·버튼으로 패드를 해제하고 다른 패드를 연결한다. | 이전 버튼 배열 재사용과 잘못된 활성 장치 선택이다. | 중립 확인 전 동작하지 않고 재연결 후 올바른 매핑으로 동작한다. |
| T06 | 트리거를 경계값 주변에서 누르고 놓는다. | 발사 떨림과 충전·해제 누락이다. | 누름·유지·해제가 의도한 횟수로 전달된다. |
| T07 | 패드가 연결된 모바일에서 가상 키를 접는다. | 입력 UI와 성능·회전 정책의 결합이다. | 기존 화질·메모리 설정과 모바일 화면 정책을 유지한다. |
| T08 | 전투에서 메뉴·지도·정비를 열고 확인·닫기를 한다. | 메뉴 클릭의 전투 발사, 지도와 카메라 동시 조작이다. | 현재 컨텍스트만 입력을 소비한다. |
| T09 | 발사 중 탭 숨김·앱 비활성화·회전을 수행한다. | 눌림·지도 토글·드래그 잔류이다. | 복귀 시 중립이며 사용자 재개 전 자동 발사하지 않는다. |
| T10 | 비표준 매핑 패드를 연결한다. | 원시 인덱스를 Xbox 배치로 오인하는 오류이다. | 가상 키를 유지하고 매핑 설정 또는 검증 프로필로 조작한다. |
| T11 | 1-1~1-3을 가상 키와 패드로 각각 진행한다. | 입력이나 저장 경계가 실제 목표·보상·재도전을 막는 오류이다. | 계획의 스테이지 1 완료 조건을 실제 플레이로 충족한다. |
| T12 | 기존 대전·보스·지도·메뉴를 대표 경로로 확인한다. | 입력 리팩터링이 기존 모드를 깨뜨리는 회귀이다. | 기존 기본 행동과 메뉴 경로를 유지한다. |
| T13 | 이후 Android 앱에서 패드·백그라운드·저장·리소스 로딩을 확인한다. | WebView·네이티브 이벤트 차이와 패키지 상대 경로 오류이다. | 실제 기기의 앱 실행과 복귀·완주를 확인한다. |
| T14 | iPhone Safari와 이후 iOS 앱을 각각 확인한다. | Android 결과를 아이폰까지 지원한 것으로 오인하는 오류이다. | 각 환경의 별도 결과가 있다. |

로컬 단위 검사는 T04·T05·T06·T08처럼 실제 상태 전환 오류를 잡는 범위에 한정한다. 버튼 상수 목록을 그대로 복제하는 테스트는 추가하지 않는다. UI 에뮬레이션·합성 패드 결과는 상태 처리 검증으로 표기하고 실제 Xbox 계열 패드나 모바일 실기기 합격과 구분한다.

## 10. 구현 완료 보고 형식과 남은 일

W00~W05를 수행할 때에는 변경 파일, 통과한 T 항목, 실제 사용한 브라우저·기기·패드, 재현 가능한 미해결 문제를 기록한다. 코드 검사·웹 완주·모바일 빌드·모바일 실기기·스토어 공개의 완료를 따로 보고한다.

현재는 이 설계 문서를 작성한 상태이며 W·M 구현은 미착수이다. Android 작업은 스테이지 1 완성 후 검토와 사용자의 별도 빌드 요청을 기다린다. 아이폰 지원은 목표 범위로 유지하며 앱 제작 환경과 시점은 별도로 정한다.
