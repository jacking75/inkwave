## 2. 발견 사항

### P01 — Windows에도 Metal 백엔드를 강제한다. 우선순위 P0이다.

근거는 [electron/main.cjs](../electron/main.cjs)의 10~14행이다. `use-angle=metal`, `force_high_performance_gpu`, `ignore-gpu-blocklist`를 플랫폼 조건 없이 넣는다. 주석의 전제는 Mac이지만 Windows도 같은 분기를 실행한다.

플랫폼 구분 누락은 확정이다. 그러나 Windows에서 해당 옵션이 무시됐는지, 다른 백엔드로 대체됐는지, GPU 초기화에 실패했는지는 미확정이다. 주석에 있는 소프트웨어 렌더링 방지 의도를 실제 동작 증거로 간주할 수 없다.

수정 목표는 Electron 호스트를 Tauri 2로 교체하는 것이다. Electron의 Metal 강제·GPU 차단 목록 우회를 새 호스트로 이식하지 않는다. Windows에서는 WebView2의 기본 경로를 사용하며 특정 GPU 백엔드 강제는 기기별 근거가 있을 때만 검토한다. 전체 하드웨어 가속을 끄는 방법은 CPU 부하를 크게 늘릴 수 있으므로 기본 해결책으로 채택하지 않는다. Tauri 전환으로 기존 three.js의 초기화·GPU 비용이 자동 해결되는 것은 아니며 P02~P06 수정도 유지한다.

### P02 — 설정 화면 진입 전에 월드와 자동 전투를 준비한다. 우선순위 P0이다.

근거는 [src/main.js](../src/main.js)의 `boot()` 233~317행, `_buildWorldNow()` 356행 부근, `_startAttract()` 745행 부근이다.

실행 순서는 텍스처 라이브러리 생성 → 소품·지형·도색·물리·내비게이션 생성 → 환경·효과 생성 → 자동 전투 생성 → 셰이더 준비 → 실제 프레임 3회 → 타이틀 표시이다. [src/game/match.js](../src/game/match.js)의 `setup()`은 일반 맵에서 양 팀 슬롯을 만들며, 자동 전투는 로컬 플레이어 없이 봇으로 구성된다. 처음부터 모든 맵을 생성한다는 뜻은 아니다. 최초 선택 맵 하나만으로도 이 준비 경로를 수행한다.

사용자는 무거운 로딩이 끝나기 전 저화질 설정에 접근할 수 없다. 메뉴에서도 자동 전투가 진행되며, 타이틀 진입 2.5초 뒤에는 `preloadLobby()`가 로비 장면을 추가 준비한다. 전체 화면 로비가 표시되면 뒤의 자동 전투 시뮬레이션·렌더링을 생략하는 기존 최적화는 있으므로 항상 두 전투가 동시에 실행된다고 확대하지 않는다.

수정은 WebGL 생성보다 먼저 DOM 기반 타이틀·옵션·입력 상태 화면을 제공하는 것이다. 기본 메뉴 배경은 정적 이미지 또는 단색으로 하고 자동 전투·로비 선행 로딩은 기본으로 시작하지 않는다. 사용자가 플레이를 선택한 뒤 필요한 맵과 캐릭터만 준비한다. 취소와 오류 표시도 3D 초기화 성공에 의존하지 않게 한다.

### P03 — 높은 초기 GPU 비용과 늦게 동작하는 자동 완화이다. 우선순위 P0이다.

근거는 [src/config.js](../src/config.js) 590~631행, [src/core/renderer.js](../src/core/renderer.js) 112~157행, [src/main.js](../src/main.js)의 `_dynRes()` 1229행 부근이다.

| 항목 | 현재 기본 경로 | 영향 |
|---|---|---|
| 화질 | `high`이다. | 장치 성능 확인 전 고비용 경로로 진입한다. |
| 해상도 | DPR 상한 1.5이다. | 고해상도 화면에서 픽셀 수가 커진다. |
| 후처리 | HalfFloat HDR, 비 Apple·비 터치에서 MSAA 4, GTAO, bloom이다. | 여러 렌더 타깃과 추가 렌더 패스를 사용한다. |
| 그림자·도색 | 각각 4096 크기를 사용한다. | 큰 GPU 자원을 시작부터 생성한다. |
| 프레임 제한 | `fpsCap: 0`이다. | 화면 주사율을 따라가며 60fps보다 높은 부하가 가능하다. 무제한 반복문이라는 뜻은 아니다. |
| 자동 해상도 | 부팅·자동 전투·ultra에서는 완화하지 않으며 `dt > 0.25`도 버린다. | 이미 수백 ms 이상 걸리는 심한 지연은 완화 집계에 들어가지 않는다. |

예를 들어 CSS 3840×2160, DPR 1 조건의 RGBA16F 색상 버퍼 하나는 약 63.3 MiB이다. 샘플 버퍼·깊이·후처리·텍스처는 별도이다. 이는 실제 전체 VRAM 사용량 추정치가 아니라 해상도 비용의 예시이다.

수정은 첫 실행에서 창 모드·제한된 해상도·낮은 화질·30fps 메뉴와 60fps 플레이 상한을 사용하고, MSAA·AO·bloom·그림자를 안전 기본값에서 끄는 것이다. 저장된 고화질 설정을 가진 사용자도 3D 초기화 전에 안전 설정으로 진입할 수 있어야 한다. 안전 설정은 기존 선호 값을 지우지 않는 세션 오버라이드로 둔다. 매우 느린 프레임도 별도 심각 지연 지표로 누적하며, 메뉴·로딩에도 비용 제한을 적용한다.

### P04 — 텍스처 생성에 동기 GPU 대기가 있다. 우선순위 P1이다.

근거는 [src/world/texlib.js](../src/world/texlib.js)의 `createTextureLibrary()` 1331행 이후이다. 재질 레이어 전체를 배열 렌더 타깃에 생성하며 세 개 색상 부착물과 밉맵을 사용한다. 레이어 렌더 루프에는 양보 지점이 없다. 마지막에는 시간 측정의 정확성을 위해 `readRenderTargetPixels()`를 호출해 GPU 완료를 기다린다. 게임 부팅 경로에서 이 함수를 `await`한다.

`async` 함수나 `compileAsync()`라는 이름만으로 내부 GPU 제출과 JavaScript 작업이 모두 비차단이 되지는 않는다. 전체 월드 컴파일 실패 후 `compile()`을 다시 호출하는 [src/main.js](../src/main.js) 291행의 경로도 이미 실패한 상황에서 무거운 재시도를 할 가능성이 있다.

수정은 제품 부팅에서 측정용 동기 읽기를 제거하고 재질 생성에 작은 배치·양보·취소 지점을 두는 것이다. 가능한 정적 텍스처는 배포 전에 준비하고, 런타임 생성이 필요한 부분만 유지한다. 예외·취소 시 렌더 타깃·XR·autoClear 복원과 임시 자원 해제를 `finally`로 보장한다. 셰이더 준비는 필요한 장면 단위로 제한하며 GPU 오류 뒤 같은 전체 컴파일을 즉시 재시도하지 않는다. 단순 `Promise.race(timeout)`는 동기 작업이나 이미 제출한 GPU 작업을 취소하지 못하므로 안전장치로 충분하지 않다.

### P05 — 후처리 재생성과 맵 교체에 해제 누락이 있다. 우선순위 P1이다.

근거는 [src/core/renderer.js](../src/core/renderer.js)의 `_buildComposer()` 115행과 `applySettings()` 167행 부근이다. 기존 composer의 두 렌더 타깃만 해제하고 GTAO·bloom·grade·출력 등의 pass를 다시 생성한다. 저장소의 [GTAOPass](../vendor/three/jsm/postprocessing/GTAOPass.js)와 [UnrealBloomPass](../vendor/three/jsm/postprocessing/UnrealBloomPass.js)는 별도의 내부 타깃·재질을 해제하는 `dispose()`를 제공한다. 현재 경로에는 이 호출이 없다. `setExtraPass()`도 composer를 재생성하므로 설정 변경 때만 발생하는 문제가 아니다.

또한 [src/main.js](../src/main.js) 359행은 이전 Decor를 장면에서만 제거한다. [src/world/decor.js](../src/world/decor.js)는 인스턴스별 CanvasTexture·geometry·material을 생성하지만 해제 메서드가 없다. 반복 교체 시 GPU 자원 유지 위험이 있다. 이것만으로 첫 실행의 긴 로딩 원인을 설명할 수는 없으므로 초기 비용과 반복 사용 누적 문제를 구분한다.

수정은 각 소유자가 생성한 자원을 정확히 한 번 해제하도록 하는 것이다. 재사용하는 `extraPass`와 공유 geometry·texture는 무조건 순회해 해제하지 않는다. composer 소유 pass와 외부 소유 pass를 구분하고 Decor도 명시적 `dispose()`를 제공한다. 월드 생성 도중 실패한 소품·텍스처까지 회수한다.

### P06 — 낮은 화질로 바꿔도 모든 큰 자원이 줄어들지는 않는다. 우선순위 P1이다.

근거는 [src/main.js](../src/main.js)의 `_setSettings()` 535행, `boot()`의 텍스처·환경 생성, `_buildWorldNow()`의 도색 생성이다. 옵션 변경은 주로 `Renderer.applySettings()`로 연결된다. 이미 생성한 텍스처 라이브러리·도색 atlas·환경 그림자 크기 전체를 이 경로에서 재구성하지 않는다.

따라서 사용자가 옵션에서 Low를 선택한 것과 저비용 자원으로 처음부터 시작한 것은 같지 않다. 수정은 즉시 변경 가능한 설정과 월드 재생성이 필요한 설정을 구분하는 것이다. 진행 중인 도색·전투를 잃지 않도록 재생성 시점과 복원 계약을 정하거나 다음 임무부터 적용됨을 명확히 표시한다. 안전 시작 옵션은 반드시 자원 할당 전에 적용한다.

### I01 — 비표준 패드를 Xbox 버튼 번호로 해석한다. 우선순위 P1이다.

근거는 [src/core/input.js](../src/core/input.js) 130~147행, [src/game/player.js](../src/game/player.js) 96~141행, [src/main.js](../src/main.js)의 `_padMenus()` 1470행 부근이다. 표준 패드를 우선 찾지만 없으면 임의의 연결된 패드를 선택한다. 소비자는 축 0~3, 버튼 0·3·5·6·7·8·9 등을 고정 의미로 사용한다.

비표준 패드에서 무반응·잘못된 축·잘못된 트리거가 생길 수 있는 확정된 구현 결함이다. 사용자의 패드가 비표준이라는 증거는 없다. 표준 패드조차 전혀 노출되지 않는 문제는 OS 인식·포커스·최초 사용자 동작·앱의 API 가용 상태를 별도로 구분해야 한다.

수정은 표준 매핑만 자동 적용하고, 비표준 장치는 검증된 프로필 또는 사용자 매핑을 거치게 하는 것이다. 연결 없음·미노출·매핑 필요·중립 대기·사용 가능 상태를 표시한다. 매핑이 없을 때 조작이 되는 것처럼 표시하지 않는다.

### I02 — 패드 재연결과 입력 초기화가 불완전하다. 우선순위 P1이다.

`pollPad()`는 연결이 없으면 즉시 반환하면서 `padPrev`를 남긴다. 패드가 교체돼도 index·id 변경을 기준으로 이전 버튼 상태를 초기화하지 않는다. `releaseAll()`은 키·마우스·일부 터치를 지우지만 패드 스냅샷·이전 버튼·에지·마우스 이동량·키 pressed 전체·지도 토글을 모두 초기화하지 않는다. 이는 [src/core/input.js](../src/core/input.js) 89~98행과 130~147행에서 확인한다.

버튼을 누른 채 연결을 끊었다가 같은 버튼이 눌린 새 장치로 돌아오면 최초 에지를 놓칠 수 있다. 반대로 초기 상태에 따라 원치 않는 확인·발사가 들어갈 수 있다. 수정은 장치 식별과 연결 세대를 관리하고, 해제·교체·포커스 이탈·화면 전환 시 held/pressed/released와 필터·반복 타이머를 함께 초기화하는 것이다. 재연결은 중립 확인 뒤 활성화한다.

### I03 — 패드 입력과 무거운 렌더링이 같은 프레임에 묶인다. 우선순위 P1이다.

근거는 [src/main.js](../src/main.js)의 `_loop()`·`_frame()`·`_padMenus()`이다. `pollPad()`와 메뉴 패드 처리는 `_frame()`에서만 이루어진다. 정상 루프는 무거운 부팅 뒤 시작되고, `_building`·`frozen`이면 프레임 전에 반환한다. GPU/메인 스레드 대기가 길어지면 입력 반응도 늦어진다. `_padMenus()`의 스틱 반복 타이머는 실제 경과 시간 대신 매 호출 `1/60`을 빼므로 저프레임에서 메뉴 이동 반복도 느려진다.

수정은 가벼운 시작 화면의 입력을 월드 생성과 분리하고 입력 폴링을 렌더 프레임 제한보다 앞에 두는 것이다. 샘플링 에지는 소비될 때까지 보존하고 한 번만 소비한다. 메뉴·지도·전투·텍스트 입력 중 소비자를 하나로 정한다. 별도 타이머 추가만으로 메인 스레드 동기 정지를 해결할 수 없으므로 P02·P04 수정이 선행한다. 이동·카메라·발사 코드 자체는 이미 존재하므로 패드 지원 전체가 없다고 판단하지 않는다.

### I04 — PC 가상 키 복구와 그래픽 정책 분리가 아직 구현되지 않았다.

근거는 [src/core/touch.js](../src/core/touch.js)의 `shouldUseTouch()`와 [src/main.js](../src/main.js) 85행 이후이다. 기본 `auto`는 coarse pointer·터치 기기 여부를 보고, 패드 사용 가능 여부를 보지 않는다. 비터치 PC에서 패드가 없거나 매핑이 안 되어도 가상 키가 자동 제공되지 않는다. 반면 터치 모드를 켜면 `memK`·기본 화질·그림자 등의 정책도 함께 달라진다.

32번 설계대로 입력 UI 표시와 성능 정책을 분리하고, 패드가 사용 불가한 PC에서도 가상 키를 복구한다. PC 가상 키는 마우스·펜 조작, 입력 중립 처리와 함께 구현한다.

### L01 — 공통 언어 설정 없이 영어 문구가 여러 계층에 직접 들어 있다.

근거는 [index.html](../index.html)의 `lang="en"`, [src/ui/menus.js](../src/ui/menus.js)의 `SETTINGS_TABS`와 화면 문구, [src/main.js](../src/main.js)의 로딩·튜토리얼·오류 문구, [src/core/touch.js](../src/core/touch.js)의 버튼 라벨이다. 기본 설정에 locale가 없으며 메뉴·HUD·설명·게임 데이터·Canvas/텍스처 문자·Electron 메뉴까지 번역 경계가 퍼져 있다. 로컬 폰트 preload도 latin 파일이다. OS 폰트 대체가 가능하므로 한글이 반드시 깨진다고 단정하지는 않는다.

## 3. 수정 태스크의 구체적인 방법과 완료 조건

### F01 — 실행 기반과 Tauri 2 전환

33번 T002~T005의 필요한 범위를 먼저 구성한다. 현재 `package.json`에는 TypeScript 컴파일·타입 검사 명령이 없고, [tools/build-dist.py](../tools/build-dist.py)는 기존 JavaScript와 리소스를 복사한다. `.ts` 파일만 추가해서는 실행 경로가 바뀌지 않는다. 게임과 호스트 어댑터는 TypeScript, Tauri 진입점과 필요한 네이티브 연결은 최소 Rust로 작성한다. 게임 로직·물리·렌더링을 Rust로 이전하지 않는다. 기존 서버는 변경하지 않는다.

**F01-A 환경 확인:** 설치된 Rust·Cargo·Visual Studio를 우선 재사용한다. 향후 읽기 전용 확인에서 Rust MSVC 타깃, Visual Studio의 C++ 데스크톱 개발 구성요소, Windows SDK, WebView2 Runtime을 각각 구분한다. Visual Studio IDE 설치만으로 C++ 도구가 준비됐다고 판단하지 않으며 재설치·업데이트를 자동 시작하지 않는다. Windows의 C++ 도구와 WebView2 요구는 [Tauri 공식 사전 요구사항](https://v2.tauri.app/start/prerequisites/)에 근거한다.

F01-A 검증: Rust·Cargo 1.89.0, `stable-x86_64-pc-windows-msvc`, Visual Studio 18 Professional의 VC.Tools.x86.x64 구성요소, Windows SDK 10.0.26100.0, WebView2 Runtime 156.0.4314.58을 읽기 전용 명령으로 확인했다. 도구 체인은 갱신하지 않았다.

**F01-B 실행 경로:** 다음은 구현 시 생성할 제안 경로이며 현재 파일이 존재한다는 뜻이 아니다.

| 대상 | 역할과 완료 조건 |
|---|---|
| `src-tauri/Cargo.toml`, `src-tauri/build.rs`, `src-tauri/src/` | Tauri 2 호스트와 필요한 플러그인을 구성한다. 버전과 잠금 파일을 일관되게 관리한다. |
| `src-tauri/tauri.conf.json` | 공통 웹 산출물을 읽고 작은 창으로 시작한다. 개발 URL과 배포 자산 경로를 분리한다. |
| `src-tauri/capabilities/` | 사용하는 창·메뉴·이벤트 기능만 허용한다. 파일·셸에 포괄 권한을 주지 않는다. |
| TypeScript 플랫폼 어댑터 | 웹에서는 웹 구현, 데스크톱에서는 Tauri 구현을 선택한다. 브라우저 경로가 Tauri 전역 객체를 요구하지 않게 한다. |
| `package.json`·웹 출력 수집 | TypeScript 출력과 기존 three.js·스타일·폰트·음원·그림·lightmap을 실제 배포 경로에 연결한다. |

정적 프런트엔드를 재사용하는 구성은 [공식 프런트엔드 안내](https://v2.tauri.app/start/frontend/), 권한 범위는 [공식 capabilities 안내](https://v2.tauri.app/security/capabilities/)를 따른다. 버전별 API·설정 키는 구현 착수 시 설치 버전에 맞춰 확인한다. 게임별 파일 접근 검증은 Rust 명령 내부에서도 수행한다.

**F01-C 호스트 계약:** 현재 [preload](../electron/preload.cjs)는 `window.inkwaveNative`에 동기 전체 화면 조회, 변경 요청, 이벤트를 제공한다. 이를 Tauri의 비동기 호출과 구독 해제 가능한 이벤트로 이전한다. 메뉴 호출자도 `Promise`를 boolean으로 오해하지 않도록 수정한다. 창 상태는 OS가 승인한 실제 상태를 기준으로 갱신한다. F11, 포커스 이탈, 최소화, 창 종료, 메뉴 한국어/영어, 허용된 외부 URL 열기를 포함한다. Electron IPC·Node API·`app://inkwave`·ASAR 전제를 그대로 복사하지 않는다.

**F01-D 자산·저장:** 개발 서버 없이 배포 앱이 로컬 자산을 읽게 한다. 음원의 탐색·반복 재생과 경로 인코딩을 검증하고, 현재 Electron의 byte-range 처리와 동등한 재생 요구를 Tauri 자산 경로에서 확인한다. 모든 음원을 Rust IPC로 통째로 전달하는 방식은 피한다. CSP는 실제 로컬 자산과 기존 통신 경로에 맞춰 설정한다.

Electron origin의 `localStorage`와 창 상태 파일이 새 WebView 저장소로 자동 이전된다고 가정하지 않는다. 기존 설정·프로필을 보존한 명시적 내보내기/가져오기 또는 검증된 이전 절차를 제공한다. 손상 데이터·버전·중복 가져오기를 처리하고 원본을 삭제하지 않는다. 이전 자료가 없으면 새 설정 한국어를 적용하되 기존 사용자 데이터를 초기화했다고 숨기지 않는다. 이전을 위해 구형 게임을 몰래 실행하지 않는다.

**F01-E 비기동 검사:** 스크립트와 Rust 빌드 훅을 먼저 검토한 다음 타입 검사·설정 검증·비기동 컴파일을 수행하는 단계이다. `cargo check`는 앱을 열지는 않지만 빌드 스크립트 실행과 CPU 사용이 있으므로 단순 파일 검토와 구분한다. 이번 문서 수정에서는 수행하지 않는다. `tauri dev`, `cargo run`, 생성 EXE 실행은 검사 명령으로 위장해 실행하지 않는다.

**F01-F 전환 완료:** F02~F06과 V01을 먼저 충족하고 V02 허용 범위에서 오프라인 시작·저장·전체 화면·음원·패드를 확인한다. 기본 시작·패키징 연결은 최신 사용자 요청으로 F01-G에서 먼저 변경한다. F01-F에서는 남은 Electron 의존성과 사용하지 않는 호스트 코드를 정리한다. 기존 `package-lock.json`의 사용자 변경을 보존하며 잠금 파일을 통째로 되돌리지 않는다. 앱 생성 성공과 성능·패드 합격은 별도 결과이다. README는 현재 명령과 미실행 검증을 구분한다.

**F01-G 구현·검증 완료:** `npm start`를 `tauri dev --no-watch --no-dev-server`, `npm run package`를 `tauri build`로 변경했다. `src-tauri/`의 최소 Rust 호스트·명시적 창/이벤트 권한·창 모드 시작 설정, TypeScript 호스트 어댑터, 별도 `.desktop-dist/` 수집 도구를 추가했다. 기존 Electron `main`과 음악 분석 prestart/prepackage 훅은 기본 실행 경로에서 제거했다. Electron 자체와 베이크 도구는 이번 범위에서 삭제하지 않았다.

시작 화면 `desktop.html`은 DOM만 사용하며 게임을 자동 import하지 않는다. 사용자가 시작 버튼을 누르면 기존 게임을 `quality=low`로 불러온다. 낮은 화질만으로 F02~F04가 완료된 것은 아니다. 전체 화면은 Tauri의 비동기 실제 상태를 캐시해 기존 게임의 동기 조회 계약에 연결하고, F11·resize 구독·정리를 구현했다. 나머지 창 상태 저장·네이티브 메뉴·외부 링크·기존 프로필 이전은 F01-C/D의 미완료 범위이다.

게임·three.js·폰트·스타일·lightmap·음원을 원본 수정 없이 수집한다. 음악 manifest가 없으면 출력 폴더에서만 목록을 생성하며 ffmpeg를 실행하지 않는다. 원본 웹 진입점은 유지하고 데스크톱 출력에서만 호스트 bootstrap으로 교체한다. 기존 게임에 동적 style 요소가 있어 CSP의 `style-src` 자동 nonce 변경만 제외하고 기존 inline 스타일 정책을 유지했다. script CSP 처리는 유지한다.

검증은 `npm run desktop:prepare` 성공, `cargo fmt -- --check` 성공, `cargo check --jobs 2` 성공, `cargo check --locked --features custom-protocol --jobs 2` 성공이다. 시작 화면의 게임 코드 비포함, bootstrap 진입, 필수 자산 존재와 문서 상대 링크·`git diff --check`도 통과했다. Rust 1.89를 유지하기 위해 Tauri Rust 2.11.6·tauri-build 2.6.3, npm API 2.11.1·CLI 2.11.5와 잠금 파일을 사용한다. 최초 TypeScript 검사에서 외부 API의 `Symbol.asyncDispose` 선언 오류가 나와 `ESNext.Disposable` 라이브러리 타입을 추가한 뒤 통과했다.

앱·게임·개발 서버를 시작하지 않았고, cargo 검사 프로세스는 모두 정상 종료했다. 설치 파일 생성·전체 화면 실동작·실제 패드·음원 재생·성능·저장 이전은 미검증이다. 기존 package-lock은 작업 전 임시 폴더에 백업한 뒤 현재 파일에서 의존성을 추가했다. 설치 도구가 취약점 9건을 보고했으며 자동 수정이나 관련 없는 패키지 갱신은 수행하지 않았다. 아이콘 도구가 생성한 모바일용 파일의 삭제는 자동 승인 검토에서 차단돼 그대로 두고 Git·Windows 번들 대상에서 제외했다.

F01 부모 완료 조건은 모든 하위 항목과 Tauri 실행 검증을 충족하는 것이다. 33번 T001의 기존 게임 실행은 현재 사용자 금지 조건 때문에 보류한다. 선행 문서의 실행 요구나 Tauri 선택을 이유로 앱을 시작하지 않는다.

### F02 — 시작 화면·화질 안전 기본값

대상은 main 부팅 조율, renderer, config, 메뉴, Tauri 초기 창 상태이다. DOM 화면 → 설정·언어·입력 상태 확인 → 명시적 플레이 → 맵 준비 순서로 바꾼다. 메뉴 자동 전투·로비 선행 로딩을 선택 기능으로 바꾼다. 렌더 픽셀 총량 상한도 두어 DPR만 제한하고 4K 창 크기를 그대로 렌더링하는 경우를 방지한다.

완료 조건은 기본 메뉴 진입에 월드·봇·WebGL이 필요하지 않고, 안전 설정이 GPU 할당 전에 적용되는 것이다. 숨김·최소화 시 시뮬레이션과 불필요한 효과 갱신을 중단한다. GPU context loss에는 무한 자동 재시작 대신 DOM 오류·복귀 경로를 제공한다.

### F03 — 준비 작업 분할

대상은 texlib, 월드 생성, 셰이더 warmup, showcase이다. 로딩 단계마다 진행·취소·실패 상태를 갖고 임시 자원의 소유자를 명시한다. 진행률만 갱신하고 한 번에 거대한 작업을 수행하는 구조를 피한다. 정적 사전 생성물은 버전·크기·현재 품질과의 호환성을 검증한다.

완료 조건은 제품 경로의 측정용 동기 GPU 읽기를 제거하고, 취소·실패에서도 렌더 상태와 임시 자원을 복구하는 것이다. 체감 로딩 개선은 V02 전까지 미검증으로 남긴다.

### F04 — 자원 해제·설정 적용

대상은 renderer의 composer·pass 소유권, Decor, 월드 교체, 품질 적용 경계이다. 공유 자원과 인스턴스 자원을 구분해 수명주기를 정의한다. bloom을 꺼도 불필요한 큰 타깃을 먼저 만들지 않도록 지연 생성도 검토한다.

완료 조건은 재구성 전 자원 해제 경로와 실패 경로가 정적으로 확인되고, 즉시 적용·다음 월드 적용 설정이 UI와 일치하는 것이다. GPU 메모리가 실제로 안정화됐는지는 V02에서만 판정한다.

### F05 — 입력 복구

33번 T006~T012·T014~T019와 연결한다. 새 병렬 입력 계층을 임의로 만들지 않고 32번의 입력 프레임 계약을 따른다. `deviceId`, 연결 세대, 매핑 상태, 중립 대기, 컨텍스트를 갖고 소비자에게 정규화된 행동을 전달한다. 메뉴 반복은 경과 시간 기준으로 바꾼다.

렌더러 없는 순수 검사에서 잡아야 할 실제 결함은 버튼을 누른 상태의 해제·교체·재연결, 프레임 사이의 짧은 에지 유실, 메뉴 확인의 전투 발사 전파, 비표준 트리거 오독, 포커스 복귀 고착이다. 합성 입력 통과는 실제 패드 인식·조작 합격을 뜻하지 않는다.

### F06 — 한국어 기본값과 영어 옵션

요구 정책은 다음과 같다. 이 절은 구현 계획이며 현재 게임에 적용됐다는 뜻이 아니다.

1. 언어는 `ko`·`en` 두 값만 사용한다. 설정이 없거나 손상됐거나 지원하지 않는 값이면 한국어로 복구한다. OS나 브라우저가 영어여도 첫 기본값은 한국어이다. 저장된 명시적 영어 선택은 유지한다.
2. 기존 `inkwave.settings`의 다른 값을 보존하면서 locale를 추가한다. 설정 저장 실패는 성공으로 숨기지 않고 한국어 또는 현재 언어로 재시도 안내를 표시한다. 저장 실패 시 현재 세션 적용과 다음 실행 유지 실패를 구분한다.
3. 옵션에 `언어 / Language`와 `한국어`·`English` 선택을 둔다. 언어 변경 시 메뉴 포커스·전투 상태를 유지하고 UI를 갱신한다. 기본값 복원은 한국어로 돌아간다. 언어 변경 때문에 월드나 GPU 자원을 재생성하지 않는다.
4. TypeScript 기반 공통 메시지 키·한국어/영어 사전·변수 보간 함수를 둔다. 메뉴·HUD·로딩·오류·도움말·결과·무기/맵 설명·패드 상태·가상 키를 포함한다. 문자열 전체를 DOM에서 찾아 바꾸는 MutationObserver 방식이나 프레임마다 문구를 재번역하는 방식은 사용하지 않는다.
5. 실제 장치에 맞는 키·버튼 표시는 번역문에 하드코딩하지 않고 행동 바인딩을 보간한다. 한국어 화면에서 패드 사용자에게 SHIFT만 안내하는 문제도 함께 해결한다.
6. `document.documentElement.lang`, 접근성 라벨, 툴팁, 초기 오류 화면도 적용한다. Canvas/SVG/절차적 텍스처에 그리는 게임 정보는 별도로 번역하고 해당 캐시만 무효화한다. 기존 캠페인 원본 그림 29장은 변경하지 않는다. 이미지에 박힌 번역 대상 문구는 목록화해 원본 보존 하에 별도 자산 작업으로 처리한다.
7. 사용자 이름·채팅·방 코드·프로토콜 ID·저장 ID는 번역하지 않는다. 제품명과 A/B/X/Y 같은 버튼 표기는 유지한다. 게임 기능 이름과 설명은 용어표로 통일한다.
8. 한글 폰트 대체 순서를 명시하고 필요하면 라이선스가 확인된 로컬 폰트를 포함한다. 오프라인 앱에서 외부 폰트 다운로드에 의존하지 않는다. 고정 너비 버튼·줄바꿈·Canvas 글자 폭도 점검한다. Tauri 자체 메뉴의 번역은 호스트 경계에서 별도로 적용한다.

완료 조건은 신규 설정 한국어, 기존 설정 이전, 영어 선택 후 재시작 유지, 한국어 복귀, 누락 키의 한국어 fallback, 양쪽 사전 키·보간 계약 일치이다. 화면 전체 번역과 글자 잘림 검증은 V02까지 미완료로 남긴다. 번역 범위가 큰 경우 메뉴·HUD·콘텐츠·호스트 하위 태스크로 나누고 일부만 끝낸 상태를 전체 한국어 지원 완료로 표시하지 않는다.

## 4. 검증과 실행 재개 경계

### V01 — 실행 없는 검증부터 수행한다.

이번에는 파일 읽기·정적 검색·Git 상태/이력·문서 링크/차이 검수와 공식 문서 확인만 수행한다. 수정 단계에서는 호출할 스크립트부터 읽고 게임·서버·브라우저·Electron·Tauri를 기동하지 않는 검사만 선택한다. 현재 없는 `typecheck`나 `test:client`를 실행 가능한 명령으로 보고하지 않는다. `npm start`, `npm run bake`, `tauri dev`, `cargo run`, smoke·botlab·stage-shots·GPU probe는 정적 검사가 아니다.

### V02 — 수정과 사용자 실행 허용 이후에 수행한다.

**이 문서 작성이나 일부 수정만으로 실행 금지가 해제되지 않는다. 현재 PC에서 자동으로 재현을 시도하지 않는다.** 실환경 확인은 수정 완료 뒤 사용자와 실행 조건을 확정한 다음 수행한다.

권장 순서는 DOM 메뉴만 확인 → 제한된 단일 장면 → 봇 없는 조작 → 제한된 전투 → 맵/품질 반복 전환이다. 가능한 별도 기기에서 먼저 수행한다. 초기 제한 예시는 작은 창·낮은 해상도·30fps·후처리/그림자 끔이며 실제 허용 범위는 실행 전에 정한다. 한 단계에서 긴 정지·context loss·비정상 메모리 증가가 보이면 다음 단계로 확대하지 않는다.

패드는 OS 인식 → 앱 노출 → 표준/비표준 매핑 → 메뉴 → 이동/카메라/공격 → 지도/정지 → 해제/재연결 순서로 확인한다. 로딩 시간·프레임 분포·프로세스 메모리·렌더 자원 수를 각각 기록한다. JavaScript 타이머만으로 OS 전체 멈춤을 막을 수 있다고 보장하지 않는다.

자동 검사, 실제 패드, 실제 웹, 데스크톱 앱 결과를 별도로 보고한다. 테스트에서 새로 시작한 프로세스만 종료하며 기존 사용자 프로세스를 일괄 종료하지 않는다. 성능 개선 수치·게임 완주·실물 패드 합격은 모두 현재 미검증이다.

## 5. 이번 산출물의 상태

R01·R02와 F01-A·F01-G는 완료이다. F01 부모와 나머지 하위 항목, F02~F06·V01~V02는 미완료이다. 후속 요청에 따라 Tauri 기본 실행·패키징 연결과 호스트를 구현했으나 전체 전환·성능·패드·언어 구현 완료로 확대하지 않는다. 31~33번의 기존 구현 체크는 변경하지 않았다. 커밋·push·배포는 수행하지 않았다.
